# ADR-001: Use SQLite as the Phase 1 data store

| Field | Value |

| Context | Penny Saver Epic A, ~5 self-hosted users, low cost |

## Context

Epic A stores expenses, recurring items, and sessions for about five users on a
self-hosted, low-cost deployment. The choice is between an embedded SQLite file
and a separate Postgres server. The store must be cheap to run, trivial to back
up, and support per-user scoping and encryption at rest (see ADR-002).

## Options

- SQLite: single file inside the Go process; no extra service; backup = copy the
  file (or Litestream). Ample for ~5 users and modest write rates.
- Postgres: a separate always-on service; stronger concurrency and tooling, but
  adds hosting cost, operational surface, and backup work not needed at this scale.

## Decision (recommended)

Use SQLite for Phase 1. It matches ~5 users, removes a paid/managed service, and
keeps deployment to one binary + one file. Revisit if concurrency or multi-node
needs arise.

## Consequences

- Cheapest and simplest to run and back up; aligns with single-binary deployment.
- Single-writer model is acceptable at this scale; heavy concurrency needs review.
- Later migration to Postgres stays possible: keep SQL standard and access behind
  one data package.

Recommendation only; awaiting explicit human approval.
